**原型**：`docs/諮詢註記_原型.html`（瀏覽器直接開，可點）

## 一、要解決的問題

**表面需求**：「系統內容都可以調整，不小心刪到會麻煩，是不是要有問卷之類的工具做紀錄。」

**拆解後的真問題**（Ray 2026/08/25 拍板）：

| # | 問題 | 這次做不做 |
|---|---|---|
| 1 | 資料真的救不回來 | ❌ **不做**。年度版本刪掉就全刪，Ray 明確表示可接受 |
| 2 | 使用者不知道救得回來 | ➖ 由「一場諮詢＝還原點」順便解掉，不另外做 |
| 3 | **資料「為什麼」變成這樣，沒有地方記** | ✅ **這次要做的** |

**成功標準**：
1. 諮詢結束時，教練**不需要事後回想補寫**就有一份完整的諮詢紀錄——它是諮詢過程的副產品。
2. 摘要開頭能回答「這次比原本優化了多少」（呼應核心命題：評判標準是**改善**不是補平）。
3. 註記的填寫率要高——若上線三個月後九成是空的，這個功能就是失敗的。

## 二、地基決策

### 2.1 註記存獨立表，主鍵掛「客戶」

**不**塞進 `plans.data`。理由：

- 註記的生命週期跟**客戶**綁，不跟年度版本綁。「這位客戶的房貸在他媽媽名下，不計入負債」明年仍成立，不該每年重打。
- 年度重製（複製去年成今年）時註記自動延續，不需要搬運邏輯。
- 順帶：不隨 plan 的 cascade 消失。這不是這次的目的，但是免費的。

⚠️ **儲存結構獨立 ≠ UI 獨立**。前端上註記框就在每個區塊底部，**不跳頁、不開彈窗**（唯一的彈窗是「結束諮詢的批次勾選」）。

### 2.2 粒度：區塊級為主，逐列資料開放列級

- **分頁級太粗**：一整頁一格＝流水帳，寫了找不到。
- **欄位級太細**：全站有 115 個 `class="sec"`，每個都掛＝沒人填。
- **定案**：手挑約 22 個真正有意義的區塊（清單見 §5），**加上**保單／收支資債／家庭成員三處的列級註記。

列級註記在**同一個區塊底部就地展開**，不另開頁面。

## 三、資料模型

### 3.1 新表 `client_notes`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid pk | |
| `client_id` | uuid → clients, **cascade** | 掛客戶，不掛 plan |
| `session_id` | uuid → consult_sessions, **set null** | null ＝日常維護 |
| `block_key` | text | 區塊代號，例：`coverage.five`、`policy:<polId>` |
| `kind` | text | `basis` 依據／`decision` 決定／`todo` 待辦 |
| `body` | text | 內容 |
| `visible` | boolean **default false** | 客戶可見。⚠️ 預設關 |
| `author_type` | text | `coach` / `client` |
| `author_id` | text | |
| `author_name` | text | 唯讀協作教練寫的要顯示作者 |
| `author_access` | text | `owner` / `viewer` / `client`。**唯讀協作與客戶寫的永遠不得 visible=true** |
| `created_at` / `updated_at` | timestamptz | |

索引：`(client_id, block_key)`、`(session_id)`、`(client_id, created_at desc)`

### 3.2 新表 `consult_sessions`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid pk | |
| `client_id` | uuid → clients, cascade | |
| `coach_id` | text → coaches | 開場的人 |
| `plan_id` | uuid → plans, **set null** | 開場當下的規劃 |
| `revision_id` | uuid → plan_revisions, **set null** | ⭐ 開場釘住的版本快照＝還原點 |
| `started_at` / `ended_at` | timestamptz | |
| `close_reason` | text | `manual` / `superseded` / `auto` |
| `review_id` | uuid → reviews, set null | 結束後產出的諮詢紀錄 |
| `metrics_before` / `metrics_after` | jsonb | 缺口等快照，供「改善多少」比對 |

⚠️ 唯一約束：一位客戶同時只能有一場未結束的 session（partial unique index on `client_id where ended_at is null`）。

### 3.3 沿用既有表

- **`reviews`** ＝ 諮詢紀錄本體。已有 `clientId/planId/date/type/attendees/summary/nextAppt`，摘要寫進 `summary`。
- **`action_items`** ＝ `kind='todo'` 的註記結束諮詢時直接生成一列（`reviewId` 帶上）。免費得到追蹤。

## 四、一場諮詢的生命週期

```
註記（永遠都在，隨時可寫、隨時看得到）
   │  沒開諮詢時寫的 → session_id = null（日常維護）
   ↓
[開始諮詢]
   ├ 建 consult_sessions 一列
   ├ ⭐ 釘住當下的 plan_revisions.id ＝ 還原點
   ├ 存 metrics_before（總缺口等）
   └ 若有「日常維護」的註記 → 問「要帶進這一場當議程嗎？」
   ↓
期間所有註記自動 session_id = 這一場
狀態列：● 諮詢進行中 · 14:32 開始 · 已記 6 則 · [結束並產摘要]
   ↓
[結束並產摘要]
   ├ 把 kind='decision' 的列成清單 → 批次勾「客戶可見」＋合規警語
   ├ 存 metrics_after
   ├ 產 reviews 一列（summary ＝ 摘要）
   └ kind='todo' → 生成 action_items
```

### ⚠️ 忘記按結束（必然會發生）

三道收尾，**忘記按結束絕不能造成資料損失**，最多只是摘要沒被人工整理過：

1. 開新的一場時**自動封掉上一場**（`close_reason='superseded'`）
2. **隔天由既有 cron 自動封場**（`close_reason='auto'`），摘要照樣產得出來
3. 狀態列常駐提醒「現在寫的東西會進紀錄」

## 六、讓人願意填的三個手法（不是加分項，是存活條件）

### 6.1 系統先寫一句，人只要接下去

每個區塊的註記框裡預先放一句依當下數字生成的話：

> 💬 壽險已備 800 萬、需求 1,124 萬，**還差 324 萬**；住院醫療日額還差 1,000 元。

教練只要接「客戶決定分兩年補足，今年先補 150 萬」。**填空的門檻比空白低一個數量級。**

⚠️ 若為了先上線砍掉這一項，等於做一堆永遠空著的框。**不可砍。**

### 6.2 有異常才醒目

缺口特別大、與去年差異超過門檻、教練手動覆蓋了系統算的值 → 註記帶變醒目。其他時候收成一行，不干擾諮詢當下的畫面。

### 6.3 填了會被客戶看到

勾了「客戶可見」的註記會印進客戶報告書的**對應章節下面**（不集中成一章）。動機從「系統要我填」變成「這段是我要講給客戶聽的」。

## 七、權限矩陣

| 身分 | 讀註記 | 寫註記 | 可勾「客戶可見」 |
|---|---|---|---|
| 主責教練 | ✅ 全部 | ✅ 全部 | ✅ |
| **唯讀協作教練** | ✅ 全部 | ✅ **可寫，標明作者** | ❌ **鎖住** |
| 客戶（客戶端） | 只看勾了可見的 | ✅ 限他自己填得到的區塊（收支、家庭、目標） | ❌ |

⚠️⚠️ **這是本案最大的地基風險**：`src/lib/clientScope.ts` 目前只有兩把尺，鐵律是「`readableClient()` 絕不可接到寫入條件上」，且 `clientScope.drift.test.ts` 逐支函式掃原始碼守著。

唯讀協作教練「可以寫註記」等於要開**第三把尺**：

```ts
/** 註記寫入範圍：主責 or 已接受的協作教練。
 *  ⚠️ 只有 lib/notes.ts 的 insert/update 自己那一列可以用，
 *     其餘任何寫入路徑一律 ownedClient()。 */
export function annotatableClient(coachId: string): SQL
```

配套**必須同時做**，否則這條線會變成唯讀被繞過的破口：

1. `annotatableClient()` 只允許出現在 `lib/notes.ts`，`clientScope.drift.test.ts` 加白名單斷言。
2. `author_access='viewer'` 的列，**資料層強制 `visible=false`**（不是 UI 擋，是寫入時覆寫）。
3. 協作教練只能改／刪**自己寫的那一列**（`author_id = me`）。

## 八、摘要與匯出

**版面**（依 `feedback_圖表優先`：首屏一張圖 ＋ ≤3 個數字）：

1. **三個數字**：這次動了幾個區塊 ／ 產生幾項待辦 ／ **總缺口 X → Y（改善 Z）**
2. **三段**：決定（最上，客戶要看的）／依據／待辦（帶負責人與期限）
3. **數字變動明細**：`<details>` 收合

**三種出口**：

| 出口 | 說明 |
|---|---|
| 存成諮詢紀錄 | 寫進 `reviews.summary`，進客戶的諮詢時間軸 |
| 匯出 PDF | 沿用既有 `printReport()` 機制（會先展開所有 `<details>`） |
| **複製純文字** | ⭐ 使用率會最高的一顆。教練諮詢完的真實行為是當場貼進 LINE。只含勾了「客戶可見」的內容 |

## 九、合規（⚠️ 會真的咬人）

嵐途的法人定位是**一般顧問公司**，無金融特許，不得從事投資顧問或保險招攬。

若教練在註記寫「建議購買 ○○ 終身壽險」而它被印進帶公司抬頭的客戶報告書 —— **那是一份招攬證據**。

因此：

1. `visible` **預設 false**，且是資料庫層的 default，不只是 UI 預設。
2. 勾選的那一刻（批次勾選視窗）顯示警語：「勾選的內容會印進帶公司抬頭的客戶文件，**不得含商品推薦或投資建議**」。
3. 唯讀協作教練與客戶寫的註記**永遠不得 visible**。
4. 客戶報告書印出的註記統一標示為「顧問註記」，與系統計算結果視覺上分開。
