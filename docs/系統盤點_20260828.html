系統有兩份引擎實作——React 端的 src/lib/engine.ts（檔頭是 @ts-nocheck，所以 tsc 對它完全無效）與教練端 public/lantu-app.html 內的鏡像。我把 152 支具名函式逐支去註解、去空白後對拍：130 支完全等價，19 支只有格式差異，真正的語意漂移只有一支（B-08）。所以引擎漂移不是主要問題——真正的問題是下面這些「算得出來但沒接上」與「錯了不噴錯」。

致命 — 數字會錯，而且錯在你要指給客戶看的地方

致命B-01

財務指標與財務階段是「把整張表加總」，完全不看收支的起訖歲

engine.ts:663-680（incTotal 664 / expTotal 670）· lantu-app.html:1807

真因
metrics() 用 sum(c.incomes, i => n(i.amount)) 加總整張表，不看 i.start / i.end；而 projection() 是逐年判斷起訖的。同一份資料，兩套口徑。
實例
把示範案年齡改成 70（收入列是 40–65、40–60，都已結束）：incTotal 仍是 1,900,000、所得穩定度 100%、儲蓄率 35.26%；同一年 projection().rows[0] 卻是 work:0, bal:-1,322,400。財務階段判成 C（啟程期），依實際現金流應該是 D（整裝期）。
影響
財務安全度、25 項比率體檢全部、財務階段（會寫進 plans.health_grade）、客戶列表的階段欄、報告書。凡是已退休、房貸已繳完、教育金已結束的客戶都踩得到——而這正是「規劃到一半」的客戶樣貌。
建議
incTotal/expTotal 改成只加總「現齡落在 start–end 內」的列（即 projection 第 0 年的口徑），或拆成 incTotalRaw（表面總額）與 incTotalNow（現齡有效），ratios/health 一律吃後者。
致命B-02

「預估壽命」與「模擬到幾歲」是兩個各走各的時鐘，拉長壽命缺口不會變大

engine.ts:747（aEnd = params.horizon || 85）vs engine.ts:309-311（le = profile.lifeExp）· 輸入欄 html:3375 與 html:3503

真因
retireNeed() 用 profile.lifeExp 算餘命，projection() 的迴圈上界卻是 params.horizon。兩個欄位互不校驗，教練只會改前者。
實例
示範案把 lifeExp 85→95、horizon 留 85：退休總需求 17,943,403 → 25,340,312（+740 萬），而現值缺口 shortPV 完全不變（541,711）。把 horizon 也改成 95，shortPV 才跳到 2,008,629（4 倍）。
影響
現值缺口、願景達成度、財務階段、缺口帳、三個處方、六根槓桿反解、諮詢前後對照。教練當著客戶的面把壽命拉長，退休需求變了、缺口不動——這個矛盾在畫面上同時看得到。
建議
aEnd = Math.max(horizon, lifeExp)，或把「模擬到幾歲」預設綁死在預估壽命上並保留覆寫。

致命B-03

預估壽命小於退休年齡時，退休需求與現值缺口一起靜靜歸零——valid 旗標算了但沒有任何人讀

engine.ts:311（m = Math.max(0, le-ra)）· engine.ts:333（回傳 valid: m>0）· html:1253-1266（html 版連 valid 欄位都沒有）

致命B-04

「保障需求反推明細」漏算父母奉養費與連帶保證，跟同一頁的五欄表對不上

html:1717-1722（毛需求算式在 1720）· 正解在 html:1578 / engine.ts:409-413 的 grossLifeNeed()

全庫有 41 筆保障需求列的客戶支出表含孝親／奉養列，明細框全部少算。差額實測 120 萬～240 萬（例：董建成 少 240 萬、林國棟 少 216 萬、多數示範案少 120 萬）。另有 1 份（林國棟）同時有個人連帶保證，差額更大。

致命B-05

保單標成「失效／停效」後，保費歸零了，保額還算在「已備保障」裡

engine.ts:358-362（existingCover）· html:1292 · 對照組 annualPremiumBy()(459)、policyBenefitRows()(609) 都有過 policyActive()

致命B-06

新客戶的自動保費列 start/end 是空字串：進了總支出，卻整段被逐年金流排除

html:1001（var span={start:'',end:''}）、html:1013 · 消費端 engine.ts:298-306（if(age<n(e.start)||age>n(e.end))return;）

真因
syncPremium() 只在「有舊的個人保費列可以繼承起訖」時才填 span；新客戶沒有舊列 → span 留空 → n('') === 0 → 每一年都命中 age > 0 而被 return。而 metrics().expTotal（見 B-01）不看起訖，照算。
影響
現值缺口、願景達成度、三個處方、缺口帳全部低估一整條保費現金流；同時支出收入比／保費支出比／低彈性支出比／儲蓄率又照算——畫面上兩組數字互相矛盾。
建議
span 預設改成 {start: profile.age, end: lifeExp || horizon}；並在 workPhaseExpense／projection 把「起訖留空」一律當成全期間有效，而不是 0–0。
生產資料實測

目前 1 筆：金思妤（2608064）的「人身保險(保障型)」年繳 20,913，start/end 皆空。這筆保費進了她的總支出、沒進她的逐年金流。數量少是因為多數客戶是從舊資料遷移來的（有舊列可繼承）——之後每一位從零建檔的新客戶都會是這樣。

致命B-07

沒有任何賺薪成員填退休年齡時，退休期支出整段從投影裡消失

engine.ts:257-268（earnerRetirePoints：if(!(ra>0))return;）· 270-281（retiredWeight 空陣列回 0）· 785
