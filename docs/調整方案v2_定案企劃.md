# 調整方案模組 v2 — 定案企劃

> 嵐途財務規劃系統｜2026-08-24 定案｜上一版＝2026-08-23 的缺口求解器（commit `89df0fe` / `e3676d5` / `47b99ce`）

---

## 一、要解決的問題

現在的 `/plan` 只能回答「支出要砍 12.4%」。教練沒辦法把它變成客戶聽得懂、當場能決定的具體動作；
而且 `shortPV` 是一個純量，說不出「哪一年之後就做不到了」。

**成功標準**：教練排完一張動作清單後，畫面能同時回答三件事——

1. 缺口補了多少（改善度，不是「補平了沒」）
2. 客戶有沒有錢做這些動作（資金勾稽）
3. 哪些願景由紅轉綠（願景時間軸）

定案後直接輸出動作流程。

## 二、Ray 的財務規劃邏輯（本次改版的地基）

### 2.1 核心命題

財務規劃的核心目的是**讓一生的理想願景有足夠的財務支撐**。
規劃完成時要確認兩件事：①現況資訊 ②未來的理想願景狀態。

兩者比較只有兩種結果：達成／不達成。但實務上——

- 能達成基本人生目標之後，就會遇到**傳承**問題，而傳承本身也是願景的一部分
- 達到目標後通常會再往更高層面追尋

> **所以結論：一定會有缺口。缺口是常態，不是異常。**

現況＝基礎、＝底。做財務調整的邏輯是**先看缺口有多少**。

### 2.2 兩個模型（原本三個，效率提升併入增加收入）

**① 增加收入**

- **1a 工作收入的提升**（優先第一）
  每個月收入提升多少錢 → 累積的資產會變多少
- **1b 理財收入的提升**（原「效率提升」併入）
  - 每月的金流：定期定額的投資或儲蓄
  - 單筆資金：由資產裡的**現金水位**決定
  - 不能流動的資產 → **變賣或貸款**（例：把多餘的房子賣掉，不動產變現金，現金再去投資）

**② 減少支出**

根據每一個項目的支出減少，**要看明細現有的狀況**，有哪些是可以刪除跟減少的。
**不會是用幾 % 來抓**，因為具體要刪減什麼項目是需要討論的。

收入與支出的差距＝每個月的結餘。

### 2.3 調整動作的記錄方式

- 用**類別**區分（投資、購買商品、買保險…），記錄**項目名稱**
- **不抓每個商品的細節**，只要教練填「使用的工具」與「達到的效果」：
  1. 年期
  2. 每個月會轉換的現金流
  3. 每年配息或分紅
  4. 增值速度

### 2.4 試算與呈現

- 每做一個動作，後面的金額和數據就改變，確認缺口是否補足
- **最上面一直保留現況，以及到未來願景整個歷程需要的資金**
- 要能回答：**做到哪一年會完成哪些事？到哪些之後就不會再完成了？**
- 還是要完成 → 進行調整
- 整個調整方案要有**試算結構**，定案之後產出**對應的動作流程**

### 2.5 錢不夠時的取捨（2026-08-24 Ray 拍板）

1. **願景順序**：一開始就先設定好有哪些願景要執行；**選定的願景當中，按時間先到的先支付**
2. **傳承規劃**：傳承是願景的一部分、不獨立計算，但客戶可以**設定不解決這個方案**（自行勾選是否處理），不處理就不納入願景
3. **資金超支＝軟提示**：財務規劃不是一次就確保終身沒問題，而是**每年動態調整**。只要大部分要解決的問題能處理即可，**特別是十年後的部分，有些許缺口都是正常的**——只要能比原本的狀態更優化就可以

## 三、與 v1 的結構性衝突（為什麼要改）

| | v1（2026-08-23） | v2 |
|---|---|---|
| 方向 | **top-down**：缺口 → 六根槓桿反解 → 比例 → 翻成金額 | **bottom-up**：逐項明細 → 具體動作 → 累加 → 回頭看缺口 |
| 輸出 | 「支出砍 12.4%」 | 「停掉第二台車，每月省 8,000」 |
| 評判 | 補平了沒（沒補平＝一片紅） | **改善了多少** |
| 缺口 | 單一純量 `shortPV` | 純量＋**事件級可負擔性**＋**近／遠兩段** |
| 報酬率 | 全域單一假設（會自我實現） | **分離池**：動作的錢用動作自己的報酬率 |

**六根槓桿的分類錯誤**：Ray 的兩個模型都是「把水加進來」，
而 `retire` / `retireLevel` / `vision` 是「把桶子變小」——它們不補缺口，是改變缺口本身。
v1 把六根平放成六條拉桿，混了兩種不同性質的東西。v2 分成兩區。

## 四、選定方案

**拉桿降級成「配額」＋ 動作清單為執行層，動作自帶報酬率走分離池。**

- 求解器**程式碼全部保留**，只換輸出形式與畫面位置
- 它不再產出方案，只回答「這條線需要生出多少錢」
- 實際填什麼由動作清單逐項排，兩邊**對帳**：配額 8,300 / 已排 6,200 / 還差 2,100

**為什麼不是全砍**：完全拿掉，教練排動作時沒有錨，只能瞎排。
**為什麼不是全留**：留著就等於還在用百分比抓，2.2 節那句話白講。

## 五、呈現格式（三層）

### 第一層｜永遠釘在最上面

**主圖＝願景時間軸**：橫軸年齡，資產曲線＋願景事件插旗。
- 做得到＝綠旗 **✓**、做不到＝紅旗 **✕**
- ⚠️ 符號是必要的不是裝飾：綠 `#8fc0a3` 與紅 `#ef6f6f` 在紅綠色盲下 ΔE 僅 7.8，
  落在「必須加輔助編碼」的區間，不能只靠顏色分辨

**三條線**：現況（灰 `#8ea3b5`）／套用動作後（金 `#f0c34e`）／零線。

**主數字從「補平了沒」改成「改善了多少」**：

> 缺口 1,034 萬 → 280 萬，**改善 73%**

**缺口按時間切兩段**：
- **10 年內＝硬問題**（紅，必須處理）
- **10 年後＝動態調整區**（琥珀，有缺口正常，逐年檢視）

底下一句話直接回答 2.4 那題：
> 「照現況走，你做得到 ○ 歲以前的所有事；第一個做不到的是 58 歲的『子女成家支援』，之後的 3 件都會落空。」

**互動控制項緊貼主圖下方**：一排動作開關 chips，點了圖當場動。

### 第二層｜缺口配額（六根改兩區）

| 補缺口（加水） | 改缺口（縮桶） |
|---|---|
| A 工作收入 · B 理財效率 · C 支出刪減 | D 退休年齡 · E 退休水準 · F 願景壓縮 |

每格只顯示三個數字：**配額／已排／還差**。

### 第三層｜動作清單（本次核心）

一列一個動作，勾掉就當場重算。欄位定稿見第六節。

其餘（配額對帳、動作明細表、資金勾稽、願景清單、動作流程）一律 `<details>` 收合。

### ⚠️ 「軟提示」有兩種，畫面上必須分開

| | 性質 | 呈現 | 擋不擋 |
|---|---|---|---|
| **未來缺口沒補平** | Ray 說的動態調整區 | 琥珀「未來缺口 280 萬」 | 不擋 |
| **當下每月資金排不出來** | 算術上這個月就執行不了 | **紅字**「每月資金超支 3 萬」 | 不擋，但要醒目 |

混成一條會讓教練把執行不了的方案交出去。

## 六、欄位定稿

### 6.1 動作表 `c.actions[]`

**一致性規則：所有流出走 `pay*`、所有流入走 `get*`。** 這條讓七個類別共用一張表。

| key | 名稱 | 型別 | 說明 |
|---|---|---|---|
| `id` | — | string | 系統給 |
| `on` | 啟用 | bool | 取消勾選＝暫時不算（試算用），預設 true |
| `cat` | 類別 | enum | 七選一，見 6.2 |
| `name` | 項目名稱 | text | 教練自己寫 |
| `tool` | 使用工具 | text | 商品／管道名稱，**不進計算** |
| `ref` | 指向明細 | ref | 指到 `c.expenses[i]` 或 `c.assets[i]` 的某一列 |
| `payFrom` / `payTo` | 投入期 起–迄（歲） | int | `payTo` 空＝只在 `payFrom` 那年 |
| `payMonthly` | 每月投入 | money | |
| `payLump` | 單筆投入 | money | 在 `payFrom` 那年一次 |
| `getFrom` / `getTo` | 給付期 起–迄（歲） | int | `getTo` 空＝終身 |
| `getMonthly` | 每月領取／每月增加 | money | |
| `getLump` | 一次領回／取得資金 | money | |
| `divYear` | 年配息／分紅 | money | |
| `divMode` | 配息處理 | enum | `reinvest` 再投入／`payout` 提領 |
| `growth` | 增值速度 | % | **這筆資金自己的年報酬率**（分離池） |
| `cover` | 保額 | money | 只有保障類填 |
| `coverKind` | 保障類別 | enum | 沿用現有險種表（壽險／意外傷殘／重大傷病／醫療雜費／薪資補償） |
| `src` | 資金來源 | enum/ref | `surplus` 現況結餘／`cash` 現金水位／`act:<id>` 指向另一列／`new` 新增收入 |
| `startY` | 執行時點 | int | 「什麼時候做」，動作流程排序用，預設＝`payFrom` |
| `note` | 備註 | text | |

系統算、不用填：`contribPV`（對缺口的貢獻）、`feasible`（資金來源夠不夠）。

### 6.2 七個類別各自的必填欄

| 類別 | 必填 | 說明 |
|---|---|---|
| `income` 增加工作收入 | getFrom / getTo / getMonthly | 每月**增加**多少 |
| `expense` 刪減支出 | **ref**→支出明細 / getFrom / getTo / getMonthly | 每月**省下**多少。⚠️ 必須指到明細某一列，不能自由填——這是 2.2 那句「逐項討論」的落點 |
| `regular` 定期定額 | payFrom / payTo / payMonthly / growth / src | |
| `lump` 單筆投入 | payFrom / payLump / growth / src | `src` 通常是 `cash` 或指向變現那一列 |
| `liquidate` 資產變現 | **ref**→資產明細 / payFrom / getLump | 填**淨變現金額**。⚠️ 賣房會連帶：租金收入消失、房貸清償、交易稅費——教練要自己扣進淨額，畫面上放提示 |
| `loan` 貸款取得資金 | getLump / payFrom / payTo / payMonthly | 利率隱含在月付裡，不另開欄位 |
| `insure` 購買保障 | payFrom / payTo / payMonthly / cover / coverKind | 可有 `getLump` 滿期金 |

### 6.3 願景側新增欄位

| key | 說明 |
|---|---|
| `on`（每個願景項目） | 是否納入本次規劃。加在 `goals[]`、`travel` / `hobby` / `luxury`。**預設 true**，既有客戶數字不動 |
| `c.legacy.on` | 是否處理傳承（Ray：客戶自行勾選） |
| `c.legacy.target` | 想留給後代的目標金額 |

⚠️ **選定閘與壓縮槓桿是兩件事，順序不能顛倒**：
`on=false` ＝這件不做，不進 `needPV`、不上時間軸；
`on=true` 才輪到 `vision` 槓桿決定「壓到 `minAmount`」。
v1 的 `vision` 槓桿是「往最低金額壓」，跟「整項拿掉」語意不同，**兩層要分開存**。

**全部都在 `plans.data` jsonb 裡，不需要 migration。**

## 八、已知風險與地雷

### 8.1 ⚠️ 重複計算（最致命）

「刪減支出 2 萬」＋「定期定額投入 2 萬」是**同一筆錢**。
兩個動作各算一次改善，缺口會憑空消失——跟企業主模組踩過的
「公司股權寫進 `c.assets` 讓退休缺口憑空消失」是同一種雷。

**防線**：每個動作**必須宣告 `src` 資金來源**，系統跑資金勾稽表：

```
每月：現況結餘 ＋ 新增工作收入 ＋ 刪減支出 − 新增投入 ＝ 剩餘結餘
單筆：現金水位 ＋ 變現所得 ＋ 貸款 − 單筆投入 ＝ 剩餘現金（vs 緊急預備金）
```

依 Ray 拍板為**軟提示不擋**，但必須跟「未來缺口」分開呈現（見第五節）。

### 8.2 ⚠️ `c.plan.levers` 與 `c.actions[]` 並存

動作清單上線後，舊的正式方案 `levers` 跟新的 `actions` 會同時有值。
報告書、生涯模擬、真實追蹤那條金色虛線目前吃的是 `levers`。

**定案**：**有動作就吃動作，`levers` 只在沒有動作時 fallback**，
並在畫面上標明現在吃的是哪一套。否則會出現
「教練排了動作、報告書卻還是舊拉桿」這種靜默錯誤。

### 8.3 ⚠️ 動作是「差額」不是「絕對值」

定期定額動作若客戶現在已經有 `c.savings[]`，新動作只能記**增加的部分**。
這條要寫進欄位說明與 UI 提示，否則教練一定會重複填。

### 8.4 ⚠️ 傳承願景現在沒有數字

`c.legacy` 只有 `heirs`（繼承人數），`estateTax` 算的是**稅**。
稅不是願景——願景是「我想留多少給孩子」。
只把稅放進 `needPV` 等於在算「為了繳稅要準備多少錢」，那不是傳承規劃。
所以新增 `c.legacy.target`，傳承願景 ＝ 目標金額 ＋ 對應遺產稅。
沒填目標金額時退回只算稅。

⚠️ 納入 `needPV` 會改變願景達成度的分母（8/23 才因為換公式讓部分客戶 B→A），
由 `c.legacy.on` 控制，預設值需 Ray 再確認（建議 false，既有客戶不動）。

### 8.5 ⚠️ 保險在試算上永遠虧

保費是流出、缺口變大，除非動作帶 `cover` 保額接回 `coverageGaps`。
這順便補掉 v1 那個「保障缺口沒有對應槓桿」的 TODO。

### 8.6 ⚠️ 資產變現的連帶效應

賣掉收租房會連帶：租金收入消失、房貸提前清償、交易稅費。
v2 不做自動連動（太細、也不見得對），改成**教練填淨變現金額＋畫面提示要扣哪幾項**。
